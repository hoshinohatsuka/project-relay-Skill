# 需求→模块映射、解耦与性能评估指南

对应 SKILL.md 的 P3、P4。这是本技能区别于通用"代码库总结"的核心方法。

## 1. P3：需求清单倒推与模块映射

**需求从哪来**（按可靠度排序）：README 功能列表 / 官网 feature 表 → CLI 命令与路由表（`argparse`/`click`/路由注册）→ CHANGELOG/release notes → 演示截图里的能力。将需求编号 R1…Rn，每条一句话。

**模块怎么数**：模块 ≠ 目录。判定标准：围绕同一数据结构或同一职责、有清晰入口（被 import/注册/路由到的单元）。典型拆法：入口层 / 业务逻辑层 / 数据访问层 / 外部集成层 / 配置与工具层。

**映射表**（`notes/03-requirement-module-map.md`）：

```markdown
| 需求 | 实现模块数 | 模块（职责） | 关键文件 | 备注 |
|---|---|---|---|---|
| R1 用户登录 | 3 | 路由(/auth)、会话管理、用户存储 | a/b.py:12, c.ts:40 | 依赖外部 IdP |
```

- 需求无对应实现 → 标 `[待确认]`，列入 P7 的"文档与实现差距"。
- 一个模块服务多个需求是正常信号（好的复用）；一个需求散落 8+ 模块是坏味道候选，交给 P4 解耦评估复核。

## 2. P4a：选型矩阵（Q4：每个模块有无单独的框架选择）

对每个模块回答：用了什么框架/库？为什么？有什么替代品？产出 `notes/04-module-matrix.md`：

```markdown
| 模块 | 选型 | 版本 | 选择理由（代码/文档证据） | 替代品 | 权衡 |
|---|---|---|---|---|---|
| Web 框架 | FastAPI | 0.115 | 自动文档+类型校验（main.py:8） | Flask, Litestar | 性能相近，生态不同 |
```

方法：从依赖清单圈出"重量级"依赖（web 框架、ORM、队列、爬虫、LLM SDK），逐个定位使用点。**每条选择理由必须标注证据级别**：
- **L1 代码证实**：使用方式能从代码直接看出（如 main.py:8 注册了 FastAPI 路由）
- **L2 维护者声明**：README/docs/commit 信息明确写了理由
- **L3 历史证据**：git log/issue 讨论能还原决策过程
- **L4 分析推断**：你自己的推断——必须显式标注，禁止伪装成 L1/L2
理由取不到就写"未见声明（L4：可能与生态惯性有关）"，不要替作者编理由。混用同类库（如两个 HTTP 客户端）要显式指出。

## 3. P4b：解耦评估（可 review 性）

逐项检查，每项给 ✔/✖/部分 + 证据：

1. **接口边界**：模块间通过显式函数/类/接口通信，还是直接翻对方内部变量？
2. **依赖方向**：是否单向（入口→逻辑→数据）？有无循环 import？
3. **可测试性**：核心逻辑能否不启动整个应用就单测？有无 `tests/` 且覆盖核心模块？
4. **可 review 性**：一个功能改动集中在少数文件，还是散落全局？全局 mutable 状态多不多？
5. **替换成本**：换掉某个重量级依赖要动多少文件？（粗估即可）

结论写成"这个项目的解耦心智模型"：哪条边界划得好、值得抄；哪条没划、代价是什么。

## 4. P4c：性能审计（不卡顿思维）

只报有代码证据的项，禁止臆测。检查清单：

- **阻塞**：同步 HTTP/DB 调用出现在请求路径或事件循环内（如 async 函数里的 `requests.get`、循环内逐条 API 调用）。
- **N+1**：循环内执行查询；ORM 关联未预加载。
- **重复计算**：同一结果多次求解、循环内重编译正则/重建对象。
- **缓存缺失**：重复拉取不变的远端资源（模型列表、配置）且无 TTL。
- **内存**：一次性读大文件/大响应进内存而非流式。
- **启动/冷启动**：import 期做重活（顶层加载大模型、建连接）。

每条格式：`症状 → 证据 file:line → 影响（定性：低/中/高） → 作者可用的修法（一句话）`。这是给学习者的"如果是我会怎么优化"素材，不是给原作者的 PR。

## 5. 覆盖率口径与采样

- **先定义分母**：候选模块集合 = 排除生成代码/vendor/测试后按模块口径（见第 1 节）列出的全部模块，写入报告。覆盖率 = 已深读模块代码行数 ÷ 候选集合代码行数。没有分母的"90%"不作数。
- 核心模块判定：入口与主数据流经过的模块优先，其次复杂度最高（最长文件/最多依赖）的模块；被排除的模块要列明排除原因。
- 快速 ≥30%、标准 ≥60%、深度 ≥90%；达不到就写实际值与原因，不许虚报。
- 深度档用子代理并行：互不重叠分区，一个 Worker 一个模块组，回传**隔离 artifact**（`artifacts/<task-id>/`）+ 路径摘要，主协调者串行合并；回传必须含 `file:line` 证据。冲突与合并细则见 multi-agent-handoff.md。
- 汇总前必须过 **P7 对抗复核**：需求有无漏映射、模块有无重复计数、选型理由是否只是 L4 推断、社区说法有无代码反证、性能建议有无证据、学习路径是否真的可执行——发现问题回到对应阶段修补，不是在报告里写"可能"。
