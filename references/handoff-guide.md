# 项目接手协议（模式B）操作细节

## 1. H0 材料清点与模式判定

输入三要素：项目路径、剩余需求或目标状态、交接材料（HANDOFF.md / 交接文档 / 聊天记录导出 / 需求文档 / 前任 AI 总结，任一即可）。

**交接文档标准搜索位**（按序查找，取最新的）：①用户直接粘贴或指定的路径；②`<项目>/.ai/handoffs/`；③`<项目>/.ai/`；④项目根 `HANDOFF*.md`/`交接文档*.md`；⑤项目父目录同名模式。多份并存时以 `.ai/HANDOFF.md` 指针指向的最新份为准，旧份归档不删。

- 有材料 → **标准接手**（走 H1–H2 对比）。
- 无材料 → **盲接**：跳过对比，但假设登记更严格（一切结论先入登记表，置信度封顶"中"）。
- 交接包裁剪：模块≤5 且需求≤3 的微型项目，允许合并为单文件 `HANDOFF.md`（内含状态/需求/禁区/验收四节），其余情况必须七件套。

**红线绑定规则**：交接文档中的"红线/禁区/DO NOT CHANGE"是经离场 AI 转述的**用户授权边界**，接手时默认绑定、必须遵守；当前用户可以当场解除某条，但接手 AI 不得自行解除。红线与代码事实冲突（如红线宣称的机制与代码不符）→ 停下问用户，不静默取舍。

## 2. H1 独立侦察（顺序不可换：先盲扫，后读材料）

先复用模式A 的 P1–P3（克隆侦察、基线测绘、需求→模块映射）在不读交接材料的情况下形成自己的认知，然后产出**五类复述**：

1. 我确定知道的事情（附 `file:line` 证据）
2. 我高度推测的事情（附依据）
3. 我不知道的事情
4. 我认为前任可能理解错误的事情（暂不写结论，留到 H2 对比）
5. 我准备验证的事情（列验证方法：跑测试/查构建/读调用链）

盲扫的意义：防止锚定效应——先读了前任的报告，扫描就会顺着报告找印证。

## 3. H2 对比与真相仲裁

逐条比对交接材料与盲扫认知，输出三列：一致 / 冲突 / 材料有而代码无。冲突按真相层级裁决：

```
L1 运行结果、测试、构建输出        （最高）
L2 源码、配置、依赖锁定、schema、git 状态
L3 明确的产品需求与验收标准
L4 架构文档与历史决策（ADR/DECISIONS）
L5 前任 AI 的分析与交接报告
L6 本技能自己的推测                 （最低，必须标注）
```

规则：代码事实 > 前任报告（前任说 JWT、代码是 session，以代码为准并记录分歧）；**任何来源的未验证断言都进假设登记表**：

```markdown
| ID | 假设 | 证据 | 置信度 | 验证方式 | 状态 |
|---|---|---|---|---|---|
| A-001 | Redis 用于 session 缓存 | src/cache/redis.ts:12 | 高 | 跑 auth 集成测试 | 待验证 |
```

假设一旦被证伪：立即修正 PROJECT_STATE 与相关结论，并在 checkpoint 注明。

## 4. H3 项目模型与追踪链（RTM）

```
项目目标 → 需求 R001… → 能力 C-xx → 模块 → 源码文件 → 测试 → 验收条件
```

模块判定口径（先声明口径再数数）：围绕同一数据结构或职责、有清晰入口（被 import/注册/路由到）的单元；不等于目录。每模块十项属性：目的/输入/输出/依赖/接口/技术栈/当前状态/已知问题/风险/验收条件。禁止为凑数拆模块。

## 5. H4 接手计划与交接包

**执行顺序纪律**：Correctness > Completeness > Maintainability > Performance。核心功能未完成前禁止大规模重构/解耦/性能优化；不"顺手优化"无关代码；安全关键项例外需用户点头。

**变更禁区**（默认禁区，用户明确批准才可动）：数据库 schema、公共 API、认证机制、已通过测试的核心模块、lockfile 重大升级、目录结构。

**Vertical Slice**：每阶段交付一条"输入→核心逻辑→输出→测试"的完整链路，而非按层横切。

**四问审查**（对计划本身，有预算地做）：
1. 第一性原理——这个设计真正解决的底层问题是什么？
2. 对抗式——如果我要故意让它失败，从哪里攻击？
3. 墨菲——什么会在最坏时刻发生？
4. 联网调研——哪些判断不能靠模型记忆？按信息源分层查证。

**七件交接包**（写入被接手项目 `.ai/`）：

| 文件 | 回答的问题 |
|---|---|
| PROJECT_STATE.md | 项目现在到底是什么状态（含基线 commit/分支/已知 bug） |
| REQUIREMENTS.md | 最终到底要做什么（R001…+验收标准） |
| ARCHITECTURE.md | 系统怎么组成（依赖方向 + 核心代码地图） |
| DECISIONS.md | 为什么这样设计（含禁区与理由） |
| TODO.md | 接下来具体做什么（执行单元 + 顺序 + 所属 Slice） |
| TEST_PLAN.md | 怎么证明真的完成（RTM 的测试列） |
| HANDOFF.md | 下一个 AI 接手第一小时干什么（硬格式：基线 commit/当前状态/禁区/下一目标/成功条件/开放问题） |
| ASSUMPTIONS.md + checkpoints.md | 假设登记 + 检查点日志 |

**常驻记忆 vs 在途状态**：PROJECT_STATE/REQUIREMENTS/ARCHITECTURE/DECISIONS 是常驻的（项目事实，长期维护）；TODO/TEST_PLAN/HANDOFF/checkpoints 是在途的（这轮工作的状态）。**工作落地并验收后，HANDOFF 应"归档"**（移入 `.ai/archive/` 或清空），避免过时交接材料毒害下一次接手。与项目已有 `AGENTS.md`/CLAUDE.md 共存：那些是静态指令（怎么干活），`.ai/` 是动态状态（干到哪了），互不覆盖。

## 6. H5 用户门禁（硬边界）

展示四样东西后停下等批准：计划（Slice 划分与顺序）、变更禁区清单、验收标准（RTM 摘要）、风险与回滚方式。用户说"开始"才进入 H6。中期要改禁区或新增需求 → 回到 H4 重新出计划再过门禁。

## 7. H6 执行与检查点

- 一次只做一个执行单元；完成即：构建/测试 → 更新 PROJECT_STATE 与 ASSUMPTIONS → git commit（信息含需求 ID，如 `R003: streaming UI`）。
- 出现以下情况立即停并回 H4/问用户：假设被证伪、需要触碰禁区、测试基线本身是坏的、范围蔓延。
- 检查点日志格式：`CP-<n> | 时间 | 需求 ID | 做了什么 | 测试结果 | commit SHA | 下一单元`。

## 8. H7 收尾与回写

五段收尾（每段对照 RTM 给 ✅/⚠️/❌ + 证据）：正确性 → 解耦 → 性能 → 可维护性 → 最终验收。禁止把"代码写完"当"验证完成"。最终输出六节：已完成（带需求 ID）/ 未完成（带原因）/ 已知问题 / 技术债 / 风险 / 下一步。同时更新七件套并归档 HANDOFF。

## 9. 模式C：交棒冻结协议（离场 AI 执行）

场景：用户发现额度即将不足、要换模型或换工具，让**当前 AI** 在下线前把会话工作固化成权威交接文档。核心不对称：离场者拥有最富上下文但它即将消失；接手者将有全新上下文但一无所知。模式C = 把不对称变成磁盘上的合约。

**权威边界（公理 11）**：交接文档权威于**意图与状态**（哪些需求、做到哪、哪些不能动、下一步是什么）；代码仍然权威于**事实**。文档自称"唯一权威进度记录"时，指的也是前者。

### C0 冻结判定
- 与用户显式确认：目标项目路径（**不猜**，猜错就写错地方）、本文档覆盖的工作范围、下一个 AI 是否已知。
- 默认**不自动 commit**（沿用范例纪律："用户从未要求 commit，不要主动 commit"）；但在文档中列未提交清单并建议用户处理。
- 下一个 AI 工具未知 → 文档必须**自足、工具无关**（尾部附无技能接手协议附录）。

### C1 事实清点（记忆 vs 磁盘）
- 优先磁盘证据：`git status`/`git diff --stat`、重跑关键测试、读回自己刚写的文件。长会话经历过上下文压缩，**记忆不可靠**。
- 每条"已完成"标注证据等级（引用 file:line 或测试数字）；分不清的写"凭记忆，未验证"。禁止把记忆写成事实。

### C2 红线提取
从本次会话的伤疤里挖：什么炸过（根因与规避）、什么不能动（用户约束/脆弱不变量）、密钥与隐私、环境与命令怪癖（如"Git Bash 下 robocopy 的 /MIR 必须配 MSYS2_ARG_CONV_EXCL"这类省下接手者一小时的细节）、来之不易的纪律（如"绝不重复计费"）。

### C3 待办规划
剩余工作按执行顺序排列：精确位置（file:line）、已定方案（用户拍板的标注"用户已定"）、验收标准、已探明的坑与兜底。

### C4 边写边落盘
**先写保命骨架，再补明细**：头部定位（三句）→ 红线 → 状态表 → 下一步第一件事，这四块先成文；然后才是已完成明细、防重探事实、测试基线。额度死在半路，骨架也在。模板见 templates.md 模板 13，八节结构：

```
头部定位（写给谁/前情/未提交警告/权威声明）
〇 红线（违反即事故）
一 原计划摘要 + 状态表（✅/⬜）
二 已完成批次明细（根因 → 修复 → 证据）
三 待办批次（按序，位置/方案/验收/坑）
四 关键架构事实（防重探清单）
五 测试基线（交接时刻的数字）
六 下一步的第一件事 + 不要做清单
附 无技能接手协议（英文 TL;DR + 真相层级 + 五类复述 + 红线纪律）
```

### C5 验证归档
- 对照自查清单：红线是否置顶且具体？状态表与磁盘证据一致？"已完成"有无证据等级？测试基线是重跑过的数字吗？接手第一步是否无歧义？无技能协议附录在吗？
- 更新 `.ai/HANDOFF.md` 指针指向最新份、checkpoints 记一笔；旧交接文档归档不删。
- 告诉用户接手那一句话：*"新会话对下一个 AI 说：用 project-relay 模式B 接手这个项目，交接文档在 `<路径>`"*——若下一个 AI 没装本技能，就说"读这份交接文档，按附录协议接手"。

### C→B 闭环
模式C 写的文档被模式B 的 H0 标准搜索位自动发现；B 端盲扫复核文档（含基线数字重跑、已完成抽查），C 端的错误声明会被 H2 仲裁抓住——**C 写合约，B 验合约**。
