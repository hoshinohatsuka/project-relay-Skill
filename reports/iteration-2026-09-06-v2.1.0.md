# Iteration Report — project-relay v2.1.0（2026-09-06）

## 1. 本次来源与动机

用户提供了两份新材料：
1. **「项目接手Skill优化想法」聊天记录**（与 DarkiIne）：多模型接力的真实动机是**停止积累单一模型的幻觉**（简单总结上下文不能减轻幻觉），实践包括按阶段换模型的流水线与**多 Agent 并行副本交叉验证**（各 Agent 同步最新状态、并行优化不同副本、副本互审）。
2. **Reverie 交接文档范例**（`交接文档-第二轮八项修复-20260831.md`）：一份真实的高质量交棒文档，其结构（红线置顶/状态表/根因明细/待办含坑/防重探事实/测试基线/下一步）被提炼为模式C 模板的八节骨架。

结论：接手方大概率用**不同的 AI**，因此模式B 需要跨 AI 加强；同时需要新增**模式C（交棒冻结）**——在额度濒尽时由**离场 AI** 主动把会话冻结成权威交接文档。v2.1.0 由此而来。

## 2. 设计决策与处置

- **模式C 落为 C0–C5**：冻结判定（路径不猜、默认不自动 commit）→ 事实清点（**记忆 vs 磁盘**核对，防离场者自己幻觉）→ 红线提取（本次会话的伤疤）→ 待办规划 → **边写边落盘**（保命骨架优先：头部/红线/状态表/下一步先成文，额度死在半路也留下有效合约）→ 验证归档（自查清单 + HANDOFF.md 指针 + 告诉用户接手那一句话）。
- **范例的"唯一权威进度记录"与真相层级的表面矛盾** → 拆解为新公理 11：文档权威于**意图与状态**，代码权威于**事实**。这是本次最重要的概念澄清。
- **红线穿越工具边界**（公理 12）：B 端 H0 把红线当作用户授权边界默认绑定，接手 AI 不得自行解除；与代码事实冲突时升级用户。
- **模式B 加强**：H0 交接文档标准搜索位（.ai/handoffs/、项目根、父目录等）；文档基线数字必须重跑复核；已完成按 file:line 抽查；用户粘贴聊天记录同样按材料处理。
- **自足协议附录**：模式C 文档尾部附"无技能接手协议"（英文 TL;DR + 真相层级 + 五类复述 + 红线纪律 + checkpoint 要求）——接力棒是文档本身，不是技能。
- **并行副本交叉验证**：采纳为 multi-agent-handoff.md 第 7 节，标注"仅用于错了很贵的关键项"，防止成本失控（对抗审查结论）。
- **拒绝/降级**：不把并行副本做成默认流程（成本）；不为交接文档增加机器校验脚本（文档质量靠 C5 自查清单 + B 端仲裁，脚本校验 markdown 章节是脆弱耦合）。

## 3. 对抗式审查（对 v2.1.0 成品）

1. **离场者幻觉污染权威**：C1 强制磁盘核对 + 文档逐条标注证据等级；B 端 H2 仲裁仍然把文档放在 L5。
2. **权威性悖论**：已用公理 11 显式拆解，模板头部固定一句"事实以代码为准"。
3. **C4 中途死亡**：边写边落盘 + 最小骨架规则写进模板；最坏情况留下"红线+状态+下一步"，仍是可用合约。
4. **红线过时被无脑服从**：B 端规则要求红线与代码冲突时必须停下问用户（不静默取舍）。
5. **触发混淆**：模式C 与"普通会话总结/周报"的边界用 2 个近邻负例守护（评测 38/38 通过）。
6. **SKILL.md 预算**：模式C 概要压缩后 13986 字节 <14KB。
7. **文档堆积矛盾**：日期+主题命名 + HANDOFF.md 指针指向最新 + 旧档归档。
